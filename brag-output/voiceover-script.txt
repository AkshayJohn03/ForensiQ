ForensiQ whiteboard lecture — narration script (scene-delimited)
Voice: Kokoro af_heart. Numbers written for TTS; exact figures appear on screen.

=== SCENE 1 — The Tuesday problem ===
Here's a scene every A I team knows. On Monday, the search assistant was fine. Since Tuesday, it gives bad answers. Confidently wrong. Sometimes refusing for no reason. Sometimes inventing things. And nobody knows why. The engineer opens the logs and finds lines. Hundreds of thousands of lines. Is it the documents? The search? The model? Debugging without a recording is Ouija board work — you ask the spirits, and you move the planchette where you hope. This is ForensiQ: a flight recorder, and a detective, for A I pipelines. In the next few minutes, we'll walk through exactly how it turns "something's wrong" into a named, evidenced, fixable diagnosis.

=== SCENE 2 — The black box ===
First: the recording. Every request through the pipeline leaves a trace — one complete record of what happened. Inside a trace are spans: one per step. Embed this. Retrieve that. Rerank. Generate the answer. Each span carries attributes — how many documents came back, what scores they got, why the model stopped. Pipelines already emit these through Langfuse, the industry's standard recorder, or as plain J S O N L files — one trace per line. ForensiQ ingests them unchanged, and normalises the vocabulary: "hybrid", "search", and "retrieval" all become "retrieve". Think of an aeroplane's black box. The incident already happened. The recording is how you stop guessing.

=== SCENE 3 — Naming the failure ===
Second: a vocabulary for failure. "The answer was bad" is not a diagnosis. ForensiQ carries a failure taxonomy — a named catalogue where every failure has an id, a stage, and a signature written in span attributes. Retrieval failures start with F, R E T. Empty retrieval set — the search returned nothing. Low recall context — it returned documents too weak to answer from. F, PROMPT: the prompt was silently truncated at the context ceiling. F, GEN: the model got stuck repeating itself, or refused when the context was actually usable, or asserted things the documents never said. F, TOOL, and F, INFRA: tool calls erroring, stages timing out, costs spiking. And every id maps to a playbook — the agreed first response. The moment you can name a failure, you stop debugging and start looking things up.

=== SCENE 4 — Two-pass classification ===
Third: how classification actually runs. The obvious design is one L L M call per trace — "does this look like a retrieval problem?" But that's slow, it's non-deterministic, and — fatal — it's unavailable exactly when you need forensics most: during the outage. ForensiQ's pass one is nine deterministic rules. Milliseconds each. Unit tested. Quoting their evidence. Rules have blinders — a novel failure with no signature gets nothing. So pass two sends only the ambiguous leftovers to an L L M, behind a protocol. And if the L L M is down, an offline fallback keeps the whole pipeline alive. The trade-off, stated honestly: a missed novel mode is a gap in coverage — not a confident wrong answer.

=== SCENE 5 — Blame ranking ===
Fourth: which stage is guilty? The classifier says what failed. The blame ranker asks where the numbers are abnormal. Every stage gets a directional z score — how many standard deviations its attributes sit from the healthy baseline. And that baseline is computed from healthy traces only, so the yardstick stays clean. A stage is accused only when the numeric anomaly and the failure label agree. Then the evidence is quoted: hit count zero. Finish reason, length. Receipts, not vibes. On fixtures with planted root causes, the true guilty stage ranks first one hundred percent of the time. That's the difference between "generation looks bad" — and "retrieve is the culprit, and here is the span that proves it."

=== SCENE 6 — The slow leak ===
Fifth: the slow leak. Some rot never crashes anything. Search quality decays a little every week. The failure mix quietly shifts. Dashboards miss it, and eyeballs miss it faster. ForensiQ treats this as statistics. It compares a recent trailing window — three days — against a fourteen day baseline, and asks: has the failure mix shifted more than luck allows? A chi square test gives a calibrated p value, and the alarm fires only below alpha — one percent. One noisy window can neither fire the alarm nor reset it: an alert needs two of the last three windows to agree. And C U S U M runs per failure class, to catch slow ramps the window is too blunt to feel. One honest caveat: drift detection measures change, not badness. Ship a prompt change that raises refusals on purpose, and it fires — for a human to bless.

=== SCENE 7 — The report ===
Sixth: the artifact. Statistics in a console don't survive the morning meeting. ForensiQ writes the R C A — a root cause analysis document. An executive summary a manager can read in one pass. The failure mix. A blame graph and an incident timeline as mermaid diagrams — diagrams that live in the repo, and diff like code. The evidence, quoted verbatim from spans. And each failure mapped to its playbook fix. It exports a postmortem, and machine readable tickets. Because the report is deterministic — no wall clock data, everything sorted — two runs over the same corpus are byte identical. So if the report changed, the pipeline changed.

=== SCENE 8 — The numbers ===
So — does it work? Measured, not claimed. On a seeded, five hundred and sixty trace corpus, with failures planted on purpose, rule classification scores precision and recall of one point zero. Every flag was real, and nothing slipped past. Blame ranking puts the true stage first — top one — one hundred percent of the time. Clustering recovers all eight planted failure families. The drift detector fires on the planted day fifteen degradation, and stays silent through the stable weeks, at alpha equals zero point zero one. One hundred twenty eight tests — all offline — in about four seconds. And the counterfactual replay is honest about being an estimate: it will tell you that raising top K does not fix an empty index.

=== SCENE 9 — Recap ===
Thirty second recap. Record everything: traces and spans are the black box. Name the failure: a taxonomy with ids and signatures — rules first, L L M for the leftovers. Point at the stage: z scores against a healthy baseline, with quoted evidence. Watch for the slow leak: chi square drift at a chosen one percent alpha, C U S U M for ramps. Then write it up: an R C A with the blame graph, the evidence, and the playbook. That's ForensiQ — the flight recorder, and the detective. When the assistant goes weird on a Tuesday, you don't guess. You read the recording.
